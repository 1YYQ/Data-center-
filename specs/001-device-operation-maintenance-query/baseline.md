# 首期开发准备基线（更新2026-11-19）

本基线沿用已确认的设备操作维护查询范围、技术路线和业务规则，将后续工作组织为可按依赖执行、可复核的批次。本文件长期维护准入和文档维护规则；当前授权与候选从STATUS和tasks顶部读取。历史“本轮仅文档/随后开发”的描述不授予本次权限。本次开工前审查允许文档、检查工具与本地审阅产物，不启动业务实现、安装、迁移、真实配置/授权变更、外发或部署。

项目当前状态只在[STATUS](../../doc/planning/STATUS.md)维护；任务状态、直接依赖、能力分段与检查点只在[tasks](tasks.md)维护。本文件定义入场条件和交接要求，不另建任务编号或进度账本。[需求追踪表](traceability.md)由[traceability.json](traceability.json)生成，记录本次候选的证据关联与缺口，不自动升级任务完成状态。

## 2. 三类入场条件

| 入场条件 | 必须具备 | 允许的结果声明 | 不由它放行的活动 |

## 4. 工作包与证据交接要求

非平凡工作包在tasks当前检查点记录：目标/FR或父任务、允许写入和副作用、直接依赖的有效能力、候选身份、输入类别、完成断言与拒绝路径、验证及恢复方法、证据位置、结果与下一就绪任务。T0仅保留目标、差异和相关检查，无需完整模板。已提交候选用commit；混合未提交工作树、字节完整性或真实证据身份才记录相关文件hash，不为每次改字强制全仓哈希。没有实际任命时引用第5节拟定职责，不把Agent写作责任当企业任命。

证据结论只使用以下范围：

| 类别 | 可以证明 | 不能证明 |
| --- | --- | --- |
| 静态文档/格式与源代码检查 | 规则/格式存在、映射有依据、来源和候选身份一致 | 接口运行、浏览器体验或业务有效性 |
| 本地合成自动化/浏览器/进程实测 | 对应代码候选和受控输入下实际覆盖的行为 | 真实审批、供应商兼容性、真实手册质量或全部FR完成 |
| 获准真实场景与人工核对 | 指定样本、角色、版本、环境、断言和时间内的结果 | 未覆盖范围及未来未变更条件下的永久保证 |

历史基线曾关联404项合并、16客户端/类型/构建和两案进程中断记录；这些不是本次重跑。文档会变更，旧候选整体文件身份不再等同当前文档基线；校验应分别证明产品代码/配置字节未变、原运行报告未变、当前文档变更可追溯。运行审计沿用未变依赖锁对应的历史记录，不伪称新查漏洞库。

失败或未知结果须保留原记录、候选和副作用状态；若存在已发送或提交未知，不换新键盲目重做。默认事故SQLite保持隔离且历史影响UNKNOWN；12张历史截图证据缺口和构建链既有高危问题继续保留，不从本轮文档检查消除。永久清理/生产恢复不属于本轮执行范围。

## 6. 文档基线的完成条件

文档准入须同时满足：

1. 已识别冲突逐条有处理位置，当前/历史/目标契约的边界可辨；本地准备、真实资料试点和发布门槛无相互替代。
2. FR-001–017、SC-001–007、T001–034均有追踪，所有关系指向真实存在的契约、场景及证据/明确缺口；FR-017不得因无运行证据被标为通过。
3. 任务准备依赖无环；准备与最终验收依赖分开，T028不反向等待用户故事，T030/T031准备不被最终验收形成自锁。
4. 每项实际证据有类别、候选、范围和限制；不能用aggregate总数证明全部需求、用模拟岗位代替签认，或把旧失败记成当前失败。
5. 真实待办有拟定责任、所需记录、影响活动及解除条件；缺项不冻结独立准备，不要求重复确认继续。
6. 本地链接/章节、FR/SC与父子任务覆盖、直接依赖无环、生成投影一致、Memory与差异检查通过。文档审查不改任务勾选、业务代码或资料；实施工作则按实际批准范围更新，不能套用文档审查的源码不变要求。旧封存证据不覆盖。
7. 当前文档与前态差异、源码保护检查、旧证据归属、当前文件hash及脱敏审阅包可复核。当前工作区仍可有既有未提交改动，快照不冒充Git提交。

## 7. 唯一入口与文档维护

从根README进入STATUS，再到tasks的“当前调度”选择动作；doc/README只作主题索引，Memory只作恢复线索。唯一入口指**一个当前状态与调度链**，不是把全部内容塞进一个文件。`.specify/feature.json`是当前feature定位源，旧`doc/planning/first-release-device-query/`仅保留跳转，不再承接正文或新引用。

| 改动类型 | 先改的事实所有者 | 同一工作单元必须检查的消费者 |
| --- | --- | --- |
| 目标、范围或业务规则 | 项目SPEC对应业务章节；首期FR/SC在feature spec | 角色职责、Plan/tasks、API/DB及quickstart受影响项；未获确认的业务取舍保留待办 |
| 接口/错误/异步状态 | API对应章节；实现以实际代码为准 | DB映射、feature契约、Web/Worker调用者及拒绝/恢复断言；明确目标与已实现差异 |
| 数据/来源/索引或生命周期 | 数据库设计对应章节 | API、迁移/回退、Worker、查询/历史/分享/撤权、备份恢复；不得只改新写入路径 |
| 技术选型或profile | 模型/前后端/Pi架构的对应事实所有者 | 锁文件、允许环境、服务准入、数据契约、Plan/tasks和受影响证据；外部能力只采信固定版官方材料及实际输出 |
| UI及工作流 | 对应角色与界面方案 | API/状态/权限边界和真实浏览器流程；候选视觉不冒充用户确认，内部诊断不塞给普通员工 |
| 任务或完成声明 | tasks对应能力/检查点，随后STATUS汇总 | 真实验收与指标原记录；其他入口只引用，不复制计数和“下一步” |
| 需求追踪 | traceability.json | 运行生成命令更新traceability.md；不能手改投影或把EV关联当当前通过 |

**变更顺序**：先定位所有者并核实授权/影响，再改规范与对应实现，做相关检查，更新任务及状态，最后运行文档检查。行为、持久字段、接口或来源身份变化使其相关旧证据失效；未变能力可复用绑定证据。仅文案变更不用重跑全部产品测试。临时脚本、截图与报告放outputs；新增持久文档必须说明未来读者和现有文件为何不足，默认原位维护。

可重复入口（不联网、不打开资料或数据库、不执行业务测试）：

```powershell
python -m src.tools.project_docs
python -m src.tools.project_docs --write-traceability
```

第一条检查本地链接/章节、入口指针、编号/任务覆盖、父子依赖无环、JSON投影和Memory；第二条只重生成追踪阅读投影后执行同样检查。输出里的本地证据链接必须另行核对；PASS只证明文档结构。新环境没有outputs时保留证据未取得的边界，不制造报告补过。尚无CI/钩子强制执行，开工/变更/交付由执行者运行；本次未配置后台续跑。

| 审查面 | 结论与调整 | 后续必须用什么证据复核 |
| --- | --- | --- |
| 方向与首期范围 | 保留设备查询优先及既定技术路线；组织答案补入feature FR/场景/追踪，计算、表格/报告及12项未启工具保持后置 | T029/T030按所有适用FR/SC验收，不以摘录或G1局部成功关闭 |
