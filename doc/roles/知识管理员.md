# 知识管理员 · 角色需求

用途：知识管理员的职责、资料治理和权限要求。实现与验收进度统一见 [项目状态](../planning/STATUS.md)，本文件不维护功能完成快照。

## 核心职责

上传、分类、登记、更新、维护与发布专业资料，并保存业务确认记录。

## 手册确认与发布责任

2026-11-14 用户明确以下分工；这是需求约定，实际流程与实现验收见项目状态。

首期先支持在系统外完成业务确认，再由知识管理员登记。两类记录分别保留：

- 业务确认：确认人、确认时间、适用范围和确认依据。
- 系统登记：登记人、登记时间。

不能把登记操作当作业务确认。后续再考虑由确认人在系统中直接完成确认，该方式尚未纳入首期要求。

确认依据通常为邮件、签字确认文件、会议纪要或工作群中的确认记录。支持上传附件或登记可追溯的来源，关联对应手册版本，保留确认人、确认时间和适用范围。依据缺失或无法核实时先标记为待确认，不直接作为正式依据。

| 责任方或事项 | 要求 |
| --- | --- |
| 熟悉设备的专业人员或业务负责人 | 确认手册的适用范围和有效版本，承担相关业务判断 |
| 知识管理员 | 根据系统外业务确认结果登记、维护和发布，分别保存业务确认与系统登记记录 |
| 未确认或存在冲突的版本 | 标记为待确认，保留原因；有权限员工的原文参考及正式使用限制见 [SPEC 首期场景](../requirements/SPEC.md#13-首期场景设备操作与维护资料查询)，不由系统自行认定适用或有效 |
| 系统管理员 | 负责权限和系统配置，不替代专业人员或业务负责人的业务判断 |

新旧版本的使用、冲突暂停、确认发布后切换及历史引用保留规则已明确，见 [SPEC 首期场景](../requirements/SPEC.md#13-首期场景设备操作与维护资料查询)。实际确认依据样本、来源核查及登记发布的具体操作、冲突复核的具体流程仍需细化；不得将知识管理员的登记或系统配置操作自动视为业务确认。

## 手册收集与首期入库

2026-11-14 用户说明，现有新手册或修订版本通常由厂家、供应商或设备负责人经邮件、工作群等渠道提供，再保存到共享文件夹或个人电脑，缺少统一收集流程。这是用户陈述，尚未核对实际文件及交接记录。

首期由知识管理员手动收集、上传，登记来源、设备型号和版本。发现重复或版本关系不清时提示核对，未经业务确认的版本保持待确认。首期以文字版和扫描版 PDF 为主，其他格式后续逐步支持；结构与出处保留、识别不清标记待核验的要求见 [SPEC 首期场景](../requirements/SPEC.md#13-首期场景设备操作与维护资料查询)。代表性样本、原文对照与修正的具体操作及上传登记交互仍需细化。

## PDF 内容核验与修正

2026-11-14 用户明确：首期由知识管理员先对照 PDF 原文核对、修正识别内容；涉及公式、单位、关键操作步骤或注意事项时，再请专业人员或业务负责人确认。

保留原始 PDF、原文位置、修正记录，以及核验人、核验时间和核验依据，供后续追溯。无法确认的内容继续标记为待核验，不用于正式说明或计算。内容核验与手册适用版本的业务确认分别判定，不能相互替代；专业确认沿用首期系统外确认及登记记录的留存要求。

## 文件等级登记与维护

2026-11-15 用户明确：单份文件等级由业务负责人或文件所属部门负责人按公司规则判定，知识管理员负责登记和维护。等级不明确时标记待确认，不默认开放；等级变更须经业务负责人确认，保留确认人、确认时间和依据。不能将登记维护操作当作自行判定或变更等级的授权，完整权限规则见 [SPEC](../requirements/SPEC.md#6-异常与权限要求)。

## 文件类别登记与维护

2026-11-15 用户明确：知识管理员按企业的业务文件类别进行登记和维护；类别规则由业务负责人确定、系统管理员配置，与文件等级分开管理。类别不单独决定访问或使用权限，仍需结合角色、授权范围、文件等级和需求分类判断；具体要求见 [SPEC](../requirements/SPEC.md#6-异常与权限要求)。

## 工作目标与待验证障碍

目标：让企业资料持续成为可找到、可判断、可复用的知识，并处理资料质量问题。以下是进一步调查清单；手册的分散收集渠道和缺少统一流程已有用户陈述支持，见上节，其余问题仍待验证。

| 工作环节 | 应调查的障碍 | 数据中心可提供的结果方向 | 需要的实际证据 |
| --- | --- | --- | --- |
| 汇集资料 | 是否不清楚资料分散在哪里、谁负责、哪些尚未沉淀 | 资料来源与责任记录、入库范围和缺失清单 | 现有文件目录、系统清单及维护责任 |
| 维护可信版本 | 是否难以识别重复、修订关系或过期内容 | 版本关联、有效状态、冲突与更新影响 | 一次真实的更新或冲突处理过程 |
| 保持内容可用 | 表格、公式、图示和脚注是否在处理后丢失关键关系 | 原文对照、问题标记、校正与再发布 | 代表性原件、处理结果与实际错误 |
| 补齐知识缺口 | 是否不知道用户经常找不到什么、哪些问题资料没有覆盖 | 授权且脱敏的缺口反馈与待补充资料；不默认暴露用户任务全文 | 已发生的咨询、未解决问题及补充资料过程 |

用户找不到答案不必然意味着增加模型能力，也可能需要补充资料、明确版本或纠正分类。资料维护是否产生实际收益，要回到用户问题能否被解决来验证。

## 员工资料问题反馈（已确认接收职责）

2026-11-17 用户确认：员工可在当前对话或手册页面提交资料问题反馈，由知识管理员后续处理。需求见 [SPEC FR-017](../requirements/SPEC.md#131-首期需求编号与覆盖边界)，候选受理接口与范围见 [API 13.4](../api/接口设计.md#134-资料问题反馈候选设计)。

员工已进一步确认在原对话/手册页查看反馈进度及管理员答复；资料更新后提示重新查询并保留旧回答。后续完整工作台、分派和状态设计已整理为[知识管理员方案](../design/知识管理员界面与对接方案.md)，仍为待评审设计；实际受理/协调名单待确认。受理关系、全部资料依赖和当前权限共同限制读取，不能因收到反馈查看用户整段对话、完整任务或其他知识库正文，无合格接收者保持受保护待分派，不默认群发。

反馈提交、处理或答复均不替代业务适用性确认、内容核验及发布门禁；需要更新手册时仍走现有维护/确认/发布流程，不自动改变版本、索引或历史回答。

## 可见范围

“需要看到”指完成本职工作的核心内容；“应该看到”指判断可信度、状态和影响所需的信息，同样属于设计要求，不是可省略的装饰；“不需要看到”指默认界面隐藏的无关细节。无权访问的数据另列为权限边界，不能仅靠隐藏界面保护。

| 类别 | 内容 |
| --- | --- |
| 需要看到：工作核心 | 授权管理范围内的资料列表、原文预览、上传、分类、版本更新与失效管理；解析内容及表格、公式、变量和单位的原文对照 |
| 应该看到：判断依据与状态 | 上传、解析和索引状态；识别失败或待核验项；重复资料、版本差异和冲突；文档有效状态与当前访问范围；资料变更记录及对关联知识的影响；权限允许的资料质量反馈 |
| 不需要看到：默认隐藏 | 模型密钥、服务器连接信息和基础设施调试细节；全局用户与角色配置；与资料维护无关的任务内容 |

## 权限边界

- **知识管理员**：资料管理权限限定到被分配的知识库或资料范围，不因管理身份自动获得全部企业资料、他人任务和结果的访问权。可查看资料当前访问范围；扩大访问范围由系统管理员按授权流程处理。
- **界面与数据**：隐藏菜单只解决信息负担，读取、检索、预览、下载和修改均需在服务端校验权限；无权访问的资料标题、摘要、引用、缓存和产物也不能泄露。
- 不可读取模型密钥及其他服务凭据；脱敏日志不能成为获取业务正文的旁路。
- 首期允许同一账号兼任多个角色，按明确批准的角色、资料范围、操作和期限组合，不能突破文件规则；完整原则见 [系统管理员](系统管理员.md#权限边界)。
- 发起普通业务任务时，应显式具备普通使用者角色或对应能力。

## 验收要求

各角色能完成本职工作；无关入口默认隐藏；直接访问接口或文件链接也不能越权；错误信息和日志不会泄露无权读取的内容。
