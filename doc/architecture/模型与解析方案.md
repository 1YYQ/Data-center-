## 3. BGE-M3 接入设计

BGE-M3 的稠密向量维度为 1024，模型说明中的最大序列长度为 8192 tokens，并支持稠密、稀疏和多向量检索能力。[官方模型卡](https://huggingface.co/BAAI/bge-m3)

- 首版设计使用 **1024 维稠密向量**；型号、公式编号等同时保留精确匹配或关键词检索路径。普通 embeddings API 是否提供稀疏或多向量输出必须核实，不因模型具备能力就假定服务已提供。
- 分别对文档片段与用户查询生成向量，二者必须使用同一向量配置。片段按章节、表格和公式关联切分，不将输入上限当作目标片段长度。
- 将实际服务限制、分词与截断策略纳入适配器；超限重新切分并保留关联，禁止静默截断公式条件。
- 接收向量时校验数量、顺序、维度及有限数值；失败结果不进入可用索引。
- 接入建议为硅基流动的 BGE-M3 embeddings 接口；官方文档列出该模型，但平台会调整模型服务，具体账户可用性与行为需实测。[平台接口文档](https://api-docs.siliconflow.cn/docs/api/embeddings-post)

## 4. MinerU VLM 接入设计

本节保留**云端备选复核**的协议边界，不再表示首轮主解析路径。首个端到端黄金样本已选Leybold P5.1.2.3；平台技术门禁与业务关键正确性核验分工、七类关键结构化内容及尚缺证据唯一见[SPEC10.6–10.8](../requirements/SPEC.md#106-质量控制风险与异常处理)。云复核不能在本地Standard失败时自动触发，须独立准入/Run/原始输出留存，不混入主批次或自动继承主批次审核。

MinerU 官方完整解析 API 提供 VLM 选项、表格与公式识别，以及包含 Markdown 和 JSON 的结果；采用异步任务方式。[官方 API 文档](https://mineru.net/doc/docs/index_en/)

- 后续获准使用云备选复核时接入完整解析API、显式选`vlm`；不以仅返回Markdown的轻量接口替代结构化解析。
- 本地文件优先经官方上传流程提交，不把本地目录变成公开下载地址。文件大小、页数、配额与支持格式以实际服务核验结果为准。
- 保存内部任务标识、远端任务标识和状态。提交、上传、轮询、下载分别记录；超时与限流使用有上限的重试。远端任务已存在时优先恢复查询，避免重复提交；提交结果未知时显式标记待核对。
- 下载后持久保存原始解析响应、Markdown、结构化内容和关联图片，不能把有时效的远端结果链接当作长期证据。
- 归一化保留页序号、阅读顺序、内容类型、表格结构、公式及上下文；坐标、置信度仅在服务实际提供时记录。缺乏可靠定位或存在关键识别歧义的内容标为待核验。
- `vlm` 是服务选项，不足以证明云端实际使用某个固定本地模型。记录服务返回的版本；未提供则标记未知，并保留请求参数、时间和结果哈希，不自行补造版本。
- 原生表格等资料可按格式直接读取结构；MinerU 作为所选解析服务，不意味着所有格式必须先转成图片。首期格式集合依据样本确定。

### 4.1 隔离环境的本地解析

2026-11-19当前HTTP本地入口已改为持久受理/Worker，固定Standard SDK直接保存到私有持久attempt工作区，并显式隔离业务配置中的远程VLM/辅助LLM；原包/资源先封存再绑定引用。此接线已过合成契约验证，真实Standard权重/目标机仍待P0验证。以下Basic/PyMuPDF段落保留既有离线基线与直接本地辅助路径，不代表HTTP主路径会自动降档；实际候选以STATUS/tasks为准。

本地 PDF 入口用 PyMuPDF 提取可读文本与有明确边线的表格，纯扫描页及只有少量文字的图像页自动交给本地 MinerU Basic。复测环境采用 **MinerU 4.2.3，ONNX 小模型包**，文字检测为 PP-OCRv6 Tiny，识别为 PP-OCRv6 Small，表格结构由 MinerU 的版面与表格模型处理。部署前在单独环境安装该版本，使用 `mineru-kit models download --tier basic --small-backend onnx` 获取公开权重，再用 `mineru-kit models verify --tier basic --small-backend onnx` 校验。权重准备完成后，将 `DATACENTER_LOCAL_MINERU_EXECUTABLE` 指向本机 `mineru-kit`，将 `DATACENTER_LOCAL_MINERU_HOME` 指向已校验的模型目录上层，应用依赖选择 `local-pdf`。

应用只调用本地档位，指定本地模型来源并关闭遥测。模型或运行环境不可用时保留原 PDF 和扫描页待核验状态。文字和表格的坐标归一到原页，印刷页码用页面边缘检测及相邻页码佐证。空值表示仍待核对。识别结果保留为待核验候选，扫描质量、错字、跨页和合并结构由管理员依据原件核对。企业环境服务准入及正式解析选型按原设计办理。 [MinerU 模型与离线配置](https://opendatalab.github.io/MinerU/usage/model_source/) · [Middle JSON 输出契约](https://opendatalab.github.io/MinerU/reference/output_files/)

扫描表格的补识复用同一 MinerU 环境的 PP-OCRv6。应用从原 PDF 逐表裁区，将相邻且位置一致的高置信文字与单一既有单元格匹配，只补入缺失的警示前段。对于首次识别为「面板键」的文字，进一步裁取小范围，只有补识同时读出相邻的「面板」「键」和中间的 ×，且能唯一对应原单元格时才填入符号。补识内容和原页坐标供管理员核验，复杂图形键通过原表裁图保留。部署将 `mineru-kit` 指向带有同目录 Python 解释器的隔离环境，以启用裁区补识。

扫描操作表出现缺失键位的动作文字时，保留原操作行并标记对应说明单元格待核验。扫描按键图例保留相邻的操作说明，已识别符号须与本行说明对应才可直接显示。例如 OK 须对应「确定键」。不确定的图形格由原表裁图提供依据，避免将 OCR 读出的字母或汉字当作图形键名。仍有该标记的原解析块需要校正后才能提交通过核验。

### 4.2 PDF 全页覆盖与原文核验（候选）

#### 现状与设计目标

2026-11-18 复核。PDF 用文字、图像、矢量路径等绘制页面，部分文件另外提供逻辑结构。页面可显示一条曲线或一个按键图形，但精确数值或操作含义可能要从坐标轴、图例或相邻说明推断，也可能已在制版或扫描中丢失。处理目标是让每一页都有处理结果，每个发现的有信息区域都有原文定位与处置状态，再按可用证据提取内容和关系。自动识别能力由独立原页标注检验。 [PDF Association 技术参考](https://pdfa.org/download-area/cheat-sheets/Basics.pdf)

原生抽取直接读取已经编码的内容，OCR 将图像里的字符转为文字，视觉模型进一步提出区域、类型和关系。三者都需要回到原页核对覆盖。只有 Markdown 或识别摘要时，输出中缺失的区域很难被发现，图表数据和按键语义也难以逐项复核。统一契约因此要求保留来源与未解释区域。

用同一张合成混合页做了三层对照。该页含原生正文、带已知数据的位图统计图和矢量示意图。

| 检查点 | 观察结果 | 对架构的要求 |
| --- | --- | --- |
| 修前本地入口（历史复现） | 当时只返回一个正文块，两处图形均无对应块。当前源码已新增`_visual_regions`，独立清点嵌入图像/矢量并输出待核验区域；本轮未重跑该页，旧结果不能证明当前仍无图形块，也不能证明已修复语义。 [当前入口](../../src/server/parsing/local_pdf.py) · [修前复现](../../outputs/pdf-architecture-review/2026-11-18/probe-result.json) | 保留已有清点机制，进一步实现逐页持久处置、内部信息区域及与语义块的独立对账；候选框不等于内容完整。 |
| 本地 MinerU 4.2.3 Basic | 直接解析该页能定位两处图形，但两处都标成 `chart`，实际只有一处为统计图。两个 `chart_body` 均为空。 [原始 Middle JSON](../../outputs/pdf-architecture-review/2026-11-18/basic-middle.json) | 分别验证定位、分类和内容提取。提供区域坐标仅证明定位有结果。 |
| 应用归一化 | 本地适配器将 `image` 和 `chart` 都映射为 `image` 块。E 的原页复核也发现图形与具体操作需按单元格建立关联。 [适配代码](../../src/server/parsing/local_mineru.py#L66) · [E 隔离验收记录](../../specs/001-device-operation-maintenance-query/artifacts/acceptance/status.md#真实原件与模拟角色演练2026-11-18) | 保留区域的分类候选、部件与关系及未核验原因，入库前检查归一化是否丢失信息。 |

#### 解析引擎与业务的接口

| 边界 | 契约 |
| --- | --- |
| 输入 | 原始 PDF 的具体版本、处理页或裁区，以及该批次绑定的解析配置。 |
| 输出 | 每页的处理状态，区域的类型、原页归一化坐标、可核对的内容及元素关系。印刷页码有证据时另存。字段缺失、类型不明或关系冲突时，保留原图定位和待核验原因。 |
| 放行 | 应用用同一契约核对页码、坐标、类型及关键关系。正式证据取自通过核验且获准发布的解析批次。对照评测的各候选结果独立保存。 |

跨引擎兼容性涉及坐标系、区域划分、阅读顺序、合并单元格和图例关联。统一 JSON 字段后仍需核对其含义与原页对应关系，单元格已被压成纯文本时应标结构待核验。首期把适配范围控制在上述契约。若未来需要增加并行引擎，先在冻结样本上证明关键项的净收益，再评估冲突裁决和人工复核成本；业务切分与引用仍按核验后的单一发布批次执行。

#### 解析与核验流程

| 阶段 | 做法与退出条件 |
| --- | --- |
| 1. 登记每一页 | 用原件页数建立页记录。以实际显示的原页为依据，合并原生文字、可见图像与矢量绘制线索、视觉版面候选。坐标统一回到原页，记录旋转及裁剪变换。文字层可用时直接读取，扫描页和混合页按区域补识。扫描整页图、照片和表格可包含更小的信息区域，父框仅代表其外边界。 |
| 2. 提取元素与关系 | 结构块保留类型候选、文字或结构、页序号、印刷页码（有据时）、坐标、原件版本、解析器及预处理修订。记录表头与跨页表、单元格与内部图标、图例与数据系列、图形键与动作及适用警告之间的关系。相同图形在不同操作行分别绑定其原文语境。复用现有内容块 `locator` 和 `structured_content`，以既有核验记录绑定具体批次与内容。 [内容块](../../src/server/models.py#L188) · [核验绑定](../../src/server/governance.py#L83) |
| 3. 对账与核验 | 用原生对象和原页渲染发现的未解释区域独立检查解析输出，保留区域对照图。每页记录已处理、空白、存在待核验区域或失败的原因。每个需处置区域记录「可核验的结构」「保留原图待核验」「有依据地标为装饰或范围外」或「无法读取及原因」。检查坐标越界、跨页误合并、缺单位或脚注、警告与操作脱离及异常空白。扩大原图局部后仍缺依据的元素及关系进入人工核验。 |
| 4. 核对数值与发布 | 图表数值标明是原文标注、按刻度量读的估计，还是当前不可取值。估计值记录刻度、单位及误差条件。警告、操作、数值和关键关系按既有人工核验与发布门禁处理。核验后按关系切分，正式查询与确定性计算只引用满足发布、适用性及授权的证据。原图、人工修订和历史引用通过版本及原件定位回查。 |

覆盖检查以原页可见内容为范围。把模型框和原生对象投影回原页，用局部渲染和图像前景检查未解释区域。扫描整页图或已识别表格内部同样检查，整页框和表格外框只提供定位。区域召回以独立原页标注为分母，未识别子元素、错误分类和错误关联分别计数。重跑产生新解析批次并保留旧引用。缺页、不可渲染或其他失败有可见状态，辅助解析内容与原件使用相同访问边界。

#### 实施次序与验收

1. 先固化合成混合页作为漏检回归。分开验证页及区域登记、归一化保护、未知区域的处置和原图回查，确认正文存在时旁边的图也有记录。
2. 用现有真实手册的已核对原页建立人工参考，另取按文件留出的混合页、扫描页和复杂版式做盲测。样本包含嵌图表格、旋转或跨页表格、图例、公式、细小警告、曲线数据及示意图。缺少的类型用获准公开材料或可控合成页补足。OmniDocBench 可参考正文、表格、公式与阅读顺序评分，图形键及操作关系单独在项目样本上标注。 [公开评测方法](https://github.com/opendatalab/OmniDocBench#evaluation)
3. 下一获准实测先核对本机最小可用性，在固定输入上比较同版 Basic 与 Standard；若主候选不达门槛，再沿同一IR比较已列PaddleOCR-VL/Docling，不默认同时引入多个引擎。测量口径与A/B/C唯一维护在[SPEC10.7](../requirements/SPEC.md#107-最小评测集与验收标准)，本节不另定阈值。此前机器检测为RTX 3060 Laptop GPU、6 GiB显存，不是目标产线配置或Standard可用证明，资源上限仍待实测。
4. 候选准入以冻结盲测集上关键内容零静默漏项、无依据关键内容零放行、正式证据均能回原页为最低门槛。明确报告待核验量及处理时长，按确认后的复核预算判断产线可用性。达标方案按本地部署和复核总成本择一；未达标时先修首次发生缺口的阶段，再用同一契约复跑。通过后用既有 E 流程复测原图、校正、重新核验以及发布预检。

关键结构化范围、业务/技术核验职责及G1首份样本已由用户明确，沿SPEC10.6–10.8执行，不再重问。仍需实际核验人/人工参考、复核工时预算、曲线估读用途/容差及目标机吞吐/许可/留存证据；云复核另核第7节准入。当前源码只有图形清点与有限补识/校正，完整IR/切分/QC和基准尚未实施；本次约束修订交付后停止等待审核。

## 5. 数据与接口边界

建议流程：原件登记 → MinerU 解析 → 结构归一化与关键内容校验 → 关联切分 → BGE-M3 向量化 → 授权范围检索 → 证据核对 → 计算与文件生成。

| 记录 | 必须保留的关联 |
| --- | --- |
| 文档版本 | 文档标识、版本、原件哈希、适用范围、访问范围 |
| 解析运行 | 文档版本、服务与实际可知版本、请求参数、输出结构版本、原始结果位置、状态及问题 |
| 内容块与片段 | 解析运行、原文位置、关联块、切分规则版本、内容哈希、核验状态 |
| 向量配置 | 模型、可知修订版本、供应商或本地服务、维度、预处理、归一化与截断规则 |
| 索引版本 | 片段集合、向量配置、构建与验证状态、当前是否启用 |

数据库优先采用 PostgreSQL + pgvector。上述内容为逻辑数据要求；具体表结构和关系单独维护在 [数据库设计](../database/数据库设计.md)。首版 BGE-M3 稠密向量按 `vector(1024)` 设计，保留配置和索引版本关联，物理索引参数经样本验证后确定；当前物理实现与验证范围见项目状态。

沿用此前讨论的目标职责划分：PostgreSQL 关系表管理用户、权限、文档版本、公式、任务及计算记录；JSONB 用于可变解析属性；pgvector 管理向量与相似度检索；原始文件、完整解析结果和生成文件独立存储。当前本地文件实现与正式存储差距见项目状态。首版不同时引入 MongoDB。

本地 Docker 与后续内网部署优先保持相同数据库和扩展版本组合。数据库版本、扩展安装、备份恢复、表结构升级及带权限过滤的检索需验证后锁定；实际部署和验证情况见项目状态。

解析接口负责提交、状态查询与结果归一化；向量接口负责批量文本到向量。业务层不直接依赖供应商响应结构。生成模型协议复用Pi适配，经API18私有模型转发执行逐请求当前授权/用途/预算复核；压缩、摘要也受同一边界。解析/向量继续由既有Python适配负责，采用Pi不产生供应商、资料外发、账号、费用或留存授权。适配层只覆盖实际接入需求，不预建完整多供应商框架。

## 6. 迁移与兼容性

| 变化 | 处理方式 | 相对成本 |
| --- | --- | --- |
| BGE-M3 API → 本地 BGE-M3 | 对齐权重修订、分词、预处理、池化、归一化及推理精度；以固定文本和检索案例验证。不能证明兼容时新建索引 | 中，取决于是否重建与数据量 |
| BGE-M3 → 其他向量模型 | 文档和查询切换至同一新配置，重新生成文档向量；即使维度相同也不混用 | 中—高 |
| MinerU 云端 → 内网解析服务 | 核对模型、流水线、输出字段与许可；新解析形成新版本，变化片段重新向量化；保留历史引用 | 中—高 |
| 本地 Docker → 内网 | 搬迁原件、结构化结果、索引及配置；准备镜像、依赖与模型文件，验证无意外外网依赖 | 取决于硬件与运行条件 |

新索引在后台构建、验证后切换；查询模型配置与索引必须一起切换。旧索引在回退窗口内保留，窗口与删除策略按企业要求确定。重建期间的资料更新、删除和权限变化需同步到新索引，禁止回退后重新暴露已撤权资料。

本地部署不保证只改服务地址即可完成。内网模型权重、代码和依赖的许可条件及硬件适配在选择具体版本时核验。

## 7. 数据流与验证

- MinerU 接收获准提交的文件或页面，向量平台接收片段及查询文本，生成服务只接收任务所需的授权内容；各数据流分别配置，不能因允许一种服务而默认允许全部资料外发。
- 凭据从环境或密钥服务读取；只保存密钥引用，日志不记录完整原文、密钥或带凭据的下载链接。
- 已存在的解析结果与索引不能因单次失败被覆盖；待核验、失败或权限不足内容不得伪装成已验证结果。

首轮验证采用获准样本，覆盖正文、复杂或跨页表格、公式上下标、变量单位、警告和脚注。先人工确定应找到的证据与关键识别结果，再检查：

1. 解析是否保留关键结构与原文定位；识别错误能否进入待核验状态。
2. 向量响应是否符合配置；型号、版本与权限过滤后是否能检索到正确证据。
3. 查询、下载与结果引用是否遵循同一权限边界。
4. 限流、超时、重复请求与过期结果链接能否被识别和恢复。
5. 切换模型配置或解析版本时，历史引用、新旧索引隔离与回退是否正确。

检索阈值、准确率、耗时、费用和人工校验成本需根据样本建立基线；目前均无实测结论。

### 11.2 档位与候选能力

【官方文档确认】3.4.5 文档分别列出 `pipeline`、`vlm-engine` 与 `hybrid-engine`，其中 Hybrid 结合原生文本提取与视觉推理，并曾提供 `effort=medium/high`。4.x 以档位表达解析质量和开销，独立选择小模型后端和 VLM 引擎。旧 Pipeline 的小模型用途可与 Basic 对照，旧 VLM/Hybrid 的复杂版面用途可与 Standard/Advanced 对照。配置、模型、档位及产物按各版本重新核实。 [3.4.5 README][mineru-legacy] · [3.x → 4.0 迁移][mineru-migration4] · [标签档位][mineru-tiers]

| 4.2.3 档位 | 官方职责与执行组件 | 项目证据和候选用途 |
| --- | --- | --- |
| Flash | 【官方文档确认】原生 PDF 文本、原生文档转换、预览与索引。扫描页和图片用 Flash OCR。 | 【需真实样本验证】可用于验证快览和原生转换。复杂图表、扫描表格的结构与警告保留需按原件验收。 |
| Basic | 【官方文档确认】以 ONNX 或 Torch 小模型执行 OCR、表格、公式与版面处理。 | 【现有代码验证】保留为现有离线基线。既有混合合成页强制调用定位到两处视觉区域，两处均分类为 `chart`，其中只有一处是统计图，且两个 body 均为空。 [现有中间结果](../../outputs/pdf-architecture-review/2026-11-18/basic-middle.json) |
| Standard | 【官方文档确认】小模型加 VLM，面向复杂版面。llama.cpp 使用注册的 Q8_0 GGUF 主模型与多模态投影文件，vLLM、LMDeploy、MLX 使用原始模型包。 | 【需真实样本验证】优先作为单独的本地候选。既有 ONNX + llama.cpp 预检通过 ONNX 包检查，GGUF 包缺少 `.mineru_complete`，Standard 推理尚未运行。 [模型预检](../../outputs/pdf-architecture-review/2026-11-18/standard-readiness.json) |
| Advanced | 【官方文档确认】沿用 Standard 的模型与运行时，增加推理计算。服务档位上限须包含 Advanced。 | 【需真实样本验证】只有 Standard 留下明确质量缺口时，比较 Advanced 的增益、延迟、资源与复核工时。 |

【官方文档确认】PDF、图像支持四个档位。Office、OpenDocument、RTF、EPUB、OFD、HTML/MHTML、CSV/TSV 使用本地 Flash 整文档路径。SDK 调用这些格式须明确传入 `tier="flash"`。`mineru-kit parse` 和本地 SDK 的 PDF 默认档位为 Standard，现有项目显式指定 Basic。文档的通用格式支持范围以调用入口为准。 [标签档位][mineru-tiers] · [标签模型注册][mineru-registry] · [模型配置][mineru-models]

### 11.3 结构、坐标与阅读顺序

| 产物 | 4.2.3 契约 | 本项目使用边界 |
| --- | --- | --- |
| Middle JSON | 【官方文档确认】协议 `schema=docvortex.middle`、`schema_version=2.0`，含 `metadata`、`extensions`、`is_full_document` 与有序 `pages[].blocks`。生产版本在 `metadata.producer.version`，有效档位和解析方式在 `extensions.mineru.tier/parse_mode`。文本可有语义行内 span，视觉父块含 body、题注或脚注，表体可为 HTML 或空间投影文本。 | 【需真实样本验证】作为本地映射首选。可用字段依实际档位、页面与块类型而定。需要确认跨页、旋转、裁切及表图候选的坐标、内容与关联。 |
| Model JSON | 【官方文档确认】`schema=docvortex.model`、`schema_version=2.0`，供分析阶段使用，含原始 blocks 与 `page_index_map`。4.2.3 公共 SDK ParseResult、CLI、自托管 API 和 WebUI 结果包中无 Model JSON。 | 【尚未确定】云 ZIP 的 `*_model.json` 有独立历史约定，结构和生成器版本需取获准实包核验。 |
| Structured Content | 【官方文档确认】按页组织的消费者字典，保留 `metadata`、`extensions`，简化自然语言 span，可提供图片来源。输出无 `schema/schema_version`，字段及转换粒度按渲染器。 | 【需真实样本验证】可作预览或后续读模型输入，依据 Middle JSON 和原件核对其简化损失。 |
| Content List V1 | 【官方文档确认】在 SDK 渲染层对严格 Middle JSON 派生的兼容格式，是按页扁平的 `list[dict]`，每项保留原始零基 `page_idx`。可用框转为 `[0,1000]` 整数，标题用 `type=text` 和 `text_level`，视觉项可带 `img_path`、题注、脚注、表体。 | 【现有代码验证】项目云适配器读取相近的扁平约定。现有适配器保留 `provider_bbox`，单位和范围待获准云实包确认。 |
| Content List V2 | 【官方文档确认】SDK 渲染层的 `list[list[dict]]`，外层依传入页序，空页保留空数组，内部 `type + content`，没有显式页号。 【现有代码验证】本机 4.2.3 渲染源码显示，V1 与 V2 的可用框共用 `int(value * 1000)` 转换。 | 【需真实样本验证】若消费抽页 V2，绑定同批输入页映射。仅凭外层数组下标无法还原间隔抽页的源页号。 |
| Markdown | 【官方文档确认】展示用字符串。默认隐藏页眉、页脚、印刷页码块和边注，保留页脚注释，合并符合条件的续段、续列表与续表。Markdown/HTML 的 FULL 模式保留页界线、页辅助块和跨页物理分段。 | 【需真实样本验证】导览与人工阅读可用，证据定位、警告完整性按原件和结构化结果校验。 |

表中输出和字段细节见 [标签输出文件][mineru-output]、[Middle JSON 规范][mineru-middle]、[渲染契约][mineru-render]。

- 【官方文档确认】Middle JSON 的 `page_idx` 为原件零基页，CLI 页选为一基，抽页也保留原页索引。固定版式 PDF/OFD 顶层块的 bbox 为 `[0,1]` 归一矩形，文本行内 span 不携带几何。PDF `extensions.docvortex_layout` 版本 1 可提供原页 `width_pt/height_pt`（PDF 点）及可选 `image_rotations`，尺寸方向与 bbox 一致，保留空页与抽页几何。 [标签输出文件][mineru-output] · [Middle JSON 规范][mineru-middle]
- 【现有代码验证】项目页定位由 `page_idx + 1` 得到 `file_page`，印刷页码单独处理。`normalized_bbox()` 校验左上、右下四个分量和范围，原页裁图按页宽高映射。顶层 `index` 表示解析顺序，项目读取 Basic 块时遍历结果序列。 【需真实样本验证】用旋转、页框差异和多栏样本核对坐标方向、题注归属、阅读顺序和跨页关系。 [本地适配器](../../src/server/parsing/local_mineru.py) · [原页坐标处理](../../src/server/parsing/local_pdf.py) · [Middle JSON 规范][mineru-middle]
- 【官方文档确认】V1/V2 兼容 renderer 保持源页与读取顺序，可分组同页连续参考条目、展平列表或目录。Markdown 默认渲染会进行续接并隐藏部分页面辅助块。结构完整、bbox 落在页内或顺序单调，都需要原件对照来支持内容正确性。 [渲染契约][mineru-render]

### 11.4 入口、素材和导出

| 入口 | 调用与输出契约 |
| --- | --- |
| `mineru-kit parse` / Python SDK | 【官方文档确认】CLI 接受 `markdown/middle_json/zip`，单文件默认 Markdown。`ParseResult.save(writer)` 写 `markdown.md`、`middle_json.json`、`structured_content.json` 和引用的 `images/`；CLI ZIP 用该保存路径。Doclib 的 `mineru parse --json` 是命令响应，带定位、状态、续读，默认请求 PDF 前 10 页。Python SDK 和 `mineru-kit parse` 默认处理 PDF 全页。 [标签输出文件][mineru-output] · [3.x → 4.0 迁移][mineru-migration4] |
| 自托管 Tasks / Router | 【官方文档确认】`POST /v1/tasks` JSON manifest（1–100 文件），按回执只 PUT 缺失文件，`GET /v1/tasks/{task_id}` 轮询，逐文件 `result_url`；取消用 `POST /v1/tasks/{task_id}/cancel`。默认包成员与上述保存包同名。另支持 `docx/html/latex` 及组合。一个文件所请求的某一导出失败会使该文件失败，其余文件可完成。 [标签 Tasks][mineru-tasks] |
| 自托管同步 HTTP | 【官方文档确认】独立 `file-parse-server` 提供 `POST /v1/file_parse`，收单文件 multipart 并调用上游 Tasks。同步完成返回附件，等待超时返回 202 与状态定位，任务继续。 [标签 file-parse][mineru-fileparse] |
| 云精解析 v4 | 【官方文档确认】Bearer Token，URL 输入走 `/api/v4/extract/task`，本地文件走 `/api/v4/file-urls/batch` 签名 PUT；批量轮询 `/api/v4/extract-results/batch/{batch_id}`，完成返回 `full_zip_url`。文档列出 `layout.json`、`*_model.json`、`*_content_list.json`、`full.md` 及可选 docx/html/latex。文件上限 200 MB、600 页，批签最多 200 文件，签名上传链接 24 小时；账户最优优先级每日 2,000 页为官方公开规则，实际账户权益与费用另核实。 [官方云 API][mineru-cloud] |

- 【官方文档确认】自托管与 CLI 包内图片使用 `images/page_{page_idx}_{parent_type}_{parent_index}.{ext}`，页号为源页零基，内嵌 HTML 图片还有从 1 开始的 body 内序号。遇同名异字节会追加 `_duplicate_n`。应解析包中真实引用。历史 ZIP 的旧路径保持原样。PDF 单个 `to_json()`/CLI Middle JSON 会省略块内 `image_base64`，需图像时从同批 ZIP 或受控原页裁区取证。官方保存拒绝未解析资产引用，不从工作目录或网络补取。 [标签输出文件][mineru-output]
- 【官方文档确认】Python 渲染层可另导出 Markdown、HTML、LaTeX、DOCX、EPUB、PDF，以及三种消费 JSON。DOCX/EPUB/PDF 用同批图片资源，显式 PDF ORIGINAL 模式要求 PDF 源、必要几何和 bbox，AUTO 可退回语义重排。WebUI 的重建 PDF 与原件预览独立，重建可用区域图导出表格或统计图。正式引用始终链接到原 PDF 与同批定位。 [标签输出文件][mineru-output] · [渲染契约][mineru-render]
- 【现有代码验证】本地 CLI 目前请求单个 Middle JSON。适配器退出临时目录时清理原始 Middle JSON，业务批次仅保存映射后内容。云适配器只读包内单个 Content List，包大小上限为 16 MiB、解压合计 64 MiB、列表文件 8 MiB，并限成员和块数。项目侧应单独验收大文档结果上限和失败可见性。 [本地适配器](../../src/server/parsing/local_mineru.py) · [业务保存](../../src/server/services.py) · [云适配器](../../src/server/parsing/mineru.py)

### 11.5 运行容量、迁移与选型门槛

- 【官方文档确认】Basic 可在 CPU 上运行。Windows x64 基础安装可用 ONNX DirectML 或 CPU 与 llama.cpp；Linux x86_64 基础安装可用 ONNX WebGPU 或 CPU；带 `full` 且有适配加速器时，Linux 优先 vLLM，Windows 可选 LMDeploy。Apple Silicon 官方推荐本机 macOS 与至少 16 GB 统一内存。官方高吞吐本地部署内存规划起点为 16 GB，NVIDIA VRAM 的规划起点为 8 GB，需核对引擎、驱动和实际空闲显存。 [标签档位][mineru-tiers] · [标签依赖][mineru-pkg]
- 【官方文档确认】API/WebUI 自动档位依据实际小模型设备选择；CPU 可用逻辑核数小于 4 时建议至 Flash，4–11 至 Basic，至少 12 至 Standard，GPU 设备可启用四档。Windows/Linux ONNX auto 对独显采用总专用内存舍入后至少 6 GiB 的判断。自动建议未独立检查系统内存。固定请求档位与服务启动上限须分别配置。 [标签档位][mineru-tiers] · [标签 Tasks][mineru-tasks]
- 【官方文档确认】自托管 API 文件解析并发 `--concurrency` 默认 1，Router 托管 worker 的 `--worker-concurrency` 默认每 worker 1。VLM 推理并发是不同的运行参数。4.2.3 服务 `--task-timeout` 默认 3,600 秒，从获得解析名额到服务端打包，区别于对上传、排队、客户端等待和模型预加载的限制。超时文件返回 `task_timeout`；独立 API 停止接收新任务等待部署方重建，托管 Router 可回收并重启 worker，其他未完成任务可能返回 `worker_restarted`。 [API 启动源码][mineru-api-cli] · [Router 启动源码][mineru-router-cli] · [4.2.3 发布说明][mineru-release]
- 【尚未确定】目标部署的 CPU/GPU、可用 RAM/VRAM、后端与驱动、可承受吞吐/时延、采购与运行预算及云账户价格均未确认。官方档位建议和 3.x 的性能数据不提供本项目吞吐证据。 【需真实样本验证】在目标机固定包版本、模型修订和后端，测冷/热启动、每页和整文档耗时、峰值 RAM/VRAM、并发下排队与超时、完成率、人工复核时间。 [标签档位][mineru-tiers] · [3.4.5 README][mineru-legacy]
- 【官方文档确认】3.x → 4.x 涉及命令、模型包、配置和数据协议变化。通用读取要求当前 schema，少数旧结果只经 Doclib 内部缓存读取器兼容。4.0.x → 4.1 的自托管破坏性变更沿用 `/v1` 前缀，移除了 `/v1/uploads`、`/v1/parse/jobs`，旧客户端与新 worker/Router 需协调升级。任务、上传与结果索引对重启的持久性须按部署核对。4.2.3 还明确拦截 `vllm<0.29.0` 配 `transformers>=5.23.0` 的组合。 [3.x → 4.0 迁移][mineru-migration4] · [4.0.x → 4.1 迁移][mineru-migration41] · [4.2.3 发布说明][mineru-release]
- 【官方文档确认】标签许可证含额外商业门槛和面向第三方的在线服务标识条款。 【尚未确定】生产部署的许可结论、所用权重的许可、云服务计费/留存以及实际外发范围待确认。 [4.2.3 许可证][mineru-license] · [标签模型注册][mineru-registry]

**优先级已由用户复审确认，能力仍需真实样本验证。** 现有隔离安装为4.2.3，下一获准批次先验证同版本地Standard及Leybold P5.1.2.3，Basic历史证据作基线，云VLM只作获准备选复核。覆盖/关系/质量验收按SPEC10.6–10.7，不以安装包校验、接口跑通、结构有效或模型自评替代业务人员原页核验；本轮不运行推理。

首期每个解析批次固定一个主引擎与一套配置。对明确缺失区域允许同引擎按原页或裁区复查。并行对照多个候选用于选型。把日常多模型串联作为默认会增加资源与权限审计成本，也难以确定冲突块、阅读顺序和引用由哪次解析负责。更换引擎、权重或输出契约时建立新批次，保留旧原件定位与已发布版本，核验并完成切换后再使用新索引。具体业务验收沿用 [4.2 节](#42-pdf-全页覆盖与原文核验候选)。
