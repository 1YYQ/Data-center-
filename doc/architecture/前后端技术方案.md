## 1. 选型与范围

前端使用 React，后端使用 Python + FastAPI，与已确定的 PostgreSQL + pgvector、BGE-M3、MinerU VLM 配合。2026-11-17用户确定Pi为核心Agent基底；SDK/Node执行宿主、工具桥接及迁移设计见 [Pi接入方案](Pi-Agent接入与改造方案.md)，设计阶段之后已授权本地实现，现有真实SDK、查询宿主与本地栈/管理子流程证据统一见[STATUS](../planning/STATUS.md)；完整目标仍待验收。模型与解析细节见 [模型与解析方案](模型与解析方案.md)。

React + FastAPI 是用户直接选择；第 2 节配套基线是依据用户要求形成的工程选型，不代表已经安装或证明版本兼容。目标是支撑三类角色的资料管理、证据查询、任务执行和结果交付，并保留从本地 Docker 迁至企业内网的路径。

## 2. 首版配套组件基线

“必要”区分能力与产品：应用需要构建、数据访问、迁移和可靠任务执行等能力，但并非只有某个指定工具才能提供。下表明确首版选用的实现。

| 组件 | 作用 | 必要性与首版决定 | 兼容性要点 |
| --- | --- | --- | --- |
| TypeScript | 检查组件属性、接口字段和任务状态的类型使用 | 非 React 硬性依赖；为持续迭代采用 | React、React DOM 与类型定义版本配套；静态类型不能替代后端运行时校验 |
| Vite | 本地开发与生产静态资源构建 | 需要构建工具，首版采用 Vite | 选择满足其要求的受支持 Node 版本；构建与类型检查分别执行；生产不使用开发服务器 |
| Ant Design | 表格、表单、上传、对话框及反馈组件 | 非强制；为减少基础交互重复实现采用 | 按 React 版本核对 peer dependencies 和浏览器支持；按需引入，仅选择一套基础 UI 库 |
| SQLAlchemy | 表映射、查询、连接池与事务边界 | 可用原生 SQL 替代；本项目统一采用 SQLAlchemy 2.x 风格 | 数据库对象与 Pydantic 接口模型分开；复杂检索允许参数化 SQL，不强行套 ORM |
| Psycopg 3 + pgvector Python 集成 | PostgreSQL 通信与向量类型适配 | 数据库驱动必要，本项目选此组合 | Python 包与数据库中的 pgvector 扩展均需配置；校验 1024 维向量读写与距离查询 |
| Alembic | 记录和执行表结构版本变更 | 数据库演进能力必要，选用 Alembic | 自动生成只是候选迁移；扩展、向量类型、索引和数据转换需检查，不能以建表替代升级 |
| Celery + RabbitMQ | 独立进程执行与消息派发 | 正式长任务需要恢复能力，选用此组合 | Worker 在 Linux 容器运行；API 与 Worker 共享任务定义，消息传标识不传完整手册 |

路由、请求状态管理库、Web 入口具体实现及生产编排配置不在本轮锁定范围；Docker Compose 继续作为已讨论的部署建议。

### 2.1 主要替代方案与取舍

| 选择 | 主要替代 | 本轮理由与成本 |
| --- | --- | --- |
| TypeScript | JavaScript | 增加类型维护，但让字段及接口修改更容易在开发时发现不一致 |
| Vite | 手动配置构建工具、引入前端全栈框架 | 当前是独立 FastAPI 后端，优先保持静态前端与简单构建链 |
| Ant Design | shadcn/ui 或自建组件 | 本项目已有大量表格、表单和管理交互；Ant Design 提供现成组件。shadcn/ui 便于修改源码，但定制组件的后续合并与维护由项目承担 |
| SQLAlchemy + Alembic | 直接驱动调用与手写 SQL 迁移 | 统一事务、模型和迁移约定；保留复杂 SQL 能力，接受依赖与学习成本 |
| Celery + RabbitMQ | Celery + Redis | 两者均为支持的消息代理；本项目尚无缓存需求，选专用消息代理，不同时引入 Redis |
| 独立任务系统 | FastAPI 进程内后台任务、数据库任务表自建执行器 | 进程内方式不足以提供本项目要求的恢复机制；自建需维护租约、重试与重复执行处理。RabbitMQ 增加一个持久化服务的运维成本 |

Ant Design 的现成组件与 shadcn/ui 的源码分发方式见各自说明；本轮没有声称 RabbitMQ 比 Redis 更快，也没有将组件选择等同于可靠任务机制已完成。[Ant Design](https://ant.design/docs/react/introduce/)、[shadcn/ui](https://ui.shadcn.com/docs)、[Celery 代理说明](https://docs.celeryq.dev/en/stable/getting-started/backends-and-brokers/index.html)

### 2.2 必须落实的兼容规则

- Vite 的 TypeScript 转译不等于类型检查；构建验证另行执行 TypeScript 检查。UI 库类型支持不代表老旧企业浏览器可运行，需确定浏览器范围。[Vite](https://vite.dev/guide/features.html)、[React TypeScript](https://react.dev/learn/typescript)、[Ant Design](https://ant.design/docs/react/introduce/)
- API 与 Worker 分别管理连接和会话，不跨请求、并发任务或进程共享 Session。若 API 使用异步数据库调用，须配套异步会话和驱动路径；同步调用不能直接阻塞异步处理路径。[SQLAlchemy 会话说明](https://docs.sqlalchemy.org/en/20/orm/session_basics.html)
- Alembic 迁移统一执行一次，不让每个应用副本启动时竞争修改数据库。破坏性变更需备份及恢复方案，不能假定降级脚本能够恢复已删除数据。[Alembic](https://alembic.sqlalchemy.org/en/latest/autogenerate.html)
- Celery 调度与 RabbitMQ 派发不保证业务“恰好一次”。任务记录先持久化，并设计派发补偿；执行前检查状态，重复消息不得重复产生业务结果。配置重试、确认及超时后，验证 Worker 中断恢复。[Celery 任务说明](https://docs.celeryq.dev/en/stable/userguide/tasks.html)
- PostgreSQL 是业务任务状态和结果的持久依据；Celery 结果后端不是第二份业务事实来源。若后续任务编排需要结果后端，再按用途配置。首版不因使用 Celery 自动添加 Redis、Flower 或周期调度服务。
- MinerU 已接收的任务通过远端任务标识恢复轮询；本地任务重试不得无条件重新上传。BGE-M3 调用按片段与向量配置识别已有结果，重试保持索引版本一致。

FastAPI 提供 OpenAPI 描述与数据校验；Vite 支持构建静态部署产物。[FastAPI 文档](https://fastapi.tiangolo.com/features/)、[Vite 文档](https://vite.dev/guide/build.html)

## 3. 接口与职责设计

具体端点、数据结构、权限与异步状态见 [接口设计](../api/接口设计.md)，持久化关系见 [数据库设计](../database/数据库设计.md)；它们定义目标规则，实现映射与当前验证边界见项目状态。

- React 负责输入、任务进度、结果及证据展示；通过后端访问资料，不直接连接数据库，也不持有模型服务密钥。
- FastAPI 负责身份与数据权限校验、业务接口、任务提交、证据组织和结果访问。角色可见范围以 `doc/roles/` 为准，不能仅靠前端隐藏入口控制权限。
- 解析、批量向量化、计算和导出交给独立执行进程；任务状态与结果保存在 PostgreSQL，页面关闭或请求中断不应使任务记录消失。
- API 与执行进程可复用同一后端代码和镜像，初期不拆分业务微服务；本地模型与解析推理服务独立部署，避免 GPU 依赖绑定 Web 后端环境。
- 前后端约定接口版本、字段类型、错误结构、分页与任务状态；精确数值明确传输格式、单位及舍入方式，正式计算由后端执行。
- 用户管理、身份认证与审计需要明确实现；框架提供接口能力不代表已具备完整业务权限模型。

pgvector 提供 SQLAlchemy 等 Python 集成；较重的任务可使用独立任务系统，而非只依赖 Web 进程中的后台回调。[pgvector Python](https://github.com/pgvector/pgvector-python)、[FastAPI 后台任务说明](https://fastapi.tiangolo.com/tutorial/background-tasks/)

## 4. 迭代与内网部署成本

| 变化 | 需要保持与处理的内容 |
| --- | --- |
| 新增角色页面或业务任务 | 保持接口与权限约定；新增页面不直接依赖供应商响应结构 |
| 修改数据库结构 | 使用版本化迁移，校验历史数据与旧任务引用，避免简单重建数据库 |
| 切换外部 API 或本地模型 | 后端适配层和能力验证负责变化；不要求前端感知服务地址与密钥 |
| 本地 Docker → 内网单机 | 复用经验证镜像，调整配置、证书与服务地址，迁移数据并演练恢复 |
| 内网无公网访问 | 前端字体、脚本及预览资源本地打包；镜像、依赖和所需模型文件提前准备；外部服务另行替换 |
| 单机 → 高可用 | 需额外设计数据库、消息服务、文件存储与调度，不能只复制应用容器 |

若采用 Vite 静态前端，Node 工具用于构建，前端产物不要求独立 Node 运行服务；Python API 和执行进程仍需运行。Compose 可通过环境覆盖配置支持部署，但不会自动解决数据恢复或高可用。[Docker 文档](https://docs.docker.com/compose/how-tos/production/)

## 6. Agent 工具体系总览（候选设计）

2026-11-17 用户要求先设计完整工具体系，再细化各界面与单条链路。本节是整体办公能力的工具目录和职责边界，不是已实现清单，也不是用户已逐项批准的函数签名。依据为 [SPEC 整体工作模型](../requirements/SPEC.md#普通使用者整体工作模型2026-11-17-范围更正)、[计算与Excel](../requirements/SPEC.md#11-候选场景公式计算与-excel)、[汇总报告](../requirements/SPEC.md#14-候选场景多资料汇总对比与报告整理) 及已确认的对话/反馈/分享要求。具体端点和持久化仍分别在 API、数据库文档集中维护。

### 6.1 三层职责

- **Agent 任务协调**：理解目标、区分已确认条件与推测、选择并组合工具、提出必要缺项、组织最终成果。理解、摘要和报告措辞是模型职责，不为每项语言动作另造工具，也不默认引入多个 Agent。
- **受控工具**：执行有明确输入、输出和副作用边界的资料读取、数值计算、表格/文档处理；同一工具可复用于不同任务，不按每个业务例子重建一套。
- **统一执行层**：服务端强制身份/权限、文件与版本校验、必要确认、幂等、任务检查点、取消/恢复、预算和审计。Agent 不能选择跳过这些要求，也不能通过另调一个“权限工具”给自己放行。

业务与强制执行边界继续在既定 FastAPI 与任务/步骤职责中实现；Agent协调复用已选Pi SDK，接入见第9节。20工具不对应20个服务，也不增加通用工作流平台或任意代码执行器。工具注册时声明可用角色、输入输出约束、允许操作与失败/恢复语义；模型只取得当前账号可调用的集合。

### 6.2 核心工具目录

下列20项覆盖已明确的完整办公任务。名称是候选内部调用名，不代表网页菜单、HTTP路径或已经存在的工具。

| 序号 | 工具及候选调用名 | 输入与实际输出 | 主要边界 |
| --- | --- | --- | --- |
| 1 | 任务上下文读取 `context.read` | 本人对话/任务标识 → 已确认条件及来源、待补项、已有成果与步骤状态 | 相关内容按当前权限投影；不读取其他对话来擅自继承条件，不把摘要或模型推断当确认 |
| 2 | 输入文件检查 `files.inspect` | 用户已上传的受控文件标识 → 类型、大小、哈希、版本、可读取性和限制 | 上传由文件服务接收；不允许模型传任意本机路径或外网URL读取文件 |
| 3 | 资料目录查找 `sources.search` | 型号、文件名、可选缩小范围 → 有权查看的文件/版本目录 | 默认范围由后端解析；目录可查看不等于可用于正式说明或计算 |
| 4 | 证据检索 `evidence.search` | 工作问题、条件和范围 → 带版本/定位的候选证据及缺口 | 型号、有效性、权限及索引资格过滤；不把候选命中自动当作充分依据 |
| 5 | 原文定位读取 `sources.read` | 文档版本及实际定位 → 正文、相关页/图表、警告/脚注及受控跳转链接 | 不静默换版，不虚构定位；解析歧义可见，缺失关键内容时停止依赖它的结论 |
| 6 | 工作簿读取 `workbooks.read` | 受控Excel文件与范围 → 工作表、单元格值/公式、单位、格式及结构关系 | 区分公式与缓存值，保留原件；无法识别项目、表头或合并区域时不猜测映射 |
| 7 | 文档与模板读取 `documents.read` | 输入文档/模板及范围 → 章节、段落、表格、样式和可填写位置 | 用于已有模板和报告结构，保留真实位置；不把解析文本当作保留格式的可编辑原件 |
| 8 | 计算准备与校验 `calculations.prepare` | 公式及其证据、输入/单位、适用条件、精度规则 → 可执行计算定义或明确缺项/冲突 | 公式提取不等于确认；关键歧义、变量、适用范围或舍入不明时暂停受影响项目 |
| 9 | 确定性计算 `calculations.run` | 经校验的定义与输入 → 数值、单位、换算/舍入及可复算记录 | 限定表达式和运算；不执行模型或文档任意代码，不以模型文字替代正式数值 |
| 10 | 表格修改预检 `workbooks.plan_changes` | 原件版本/哈希、已确认项目/区域/单元格映射与目标内容 → 拟修改位置、前后差异及必要确认事项 | 检查越界、覆盖和格式影响；已有结果更新必须取得绑定本次差异的员工确认 |
| 11 | 表格生成与修改 `workbooks.apply_changes` | 通过预检的变更及所需确认 → 新工作簿候选、实际修改清单 | 支持按任务新建、填写或追加；原件不动，保护原始数据和要求保留的格式，不写入未确认区域 |
| 12 | 表格公式重算 `workbooks.recalculate` | 修改后的工作簿及公式依赖 → 重算值、错误和实际支持/未验证项 | 不把旧缓存值当新结果；不自动执行宏或外部连接，不支持的公式/依赖明确标为未验证 |
| 13 | 报告编制 `documents.compose` | 任务要求、模板/结构、内容和证据 → 可编辑Word候选及来源映射 | 保留模板约定、版本、缺失/冲突/待确认内容，不编造资料或自动形成业务批准 |
| 14 | 成果核验 `artifacts.validate` | 成果、任务约定、输入/修改/来源记录 → 各项检查结果、问题与验证边界 | 计算、公式错误、单元格范围、原始数据/格式、来源和文件可打开性按任务检查；无法检查项不能记为通过 |
| 15 | 成果预览 `artifacts.preview` | 受控成果版本 → 对应的表格/文档/结果预览与明确状态 | 预览绑定同一文件版本，不把渲染成功当计算或业务正确；不隐含承诺网页单元格编辑器 |
| 16 | 成果交付 `artifacts.deliver` | 成果及核验结果 → 主结果摘要、可编辑文件和来源/计算/修改明细链接 | 先校验交付条件和当前操作权限；局部成果明确未完成部分，交付不等于人工复核通过 |
| 17 | 缺项与确认 `tasks.request_input` | 受影响项目、所缺参数或拟变更差异 → 原对话中的补充请求与确认记录 | 确认绑定具体任务/版本/动作，不让模型代替用户确认；不重新追问仍有效的已确认条件 |
| 18 | 任务查看与控制 `tasks.control` | 本人任务、允许动作 → 状态、检查点、取消/恢复结果 | 支持跨消息与多项目恢复；在途副作用未知时先核对，不能盲目重发或重复修改 |
| 19 | 单条回答分享 `answers.share` | 选定回答、接收者、期限或撤销动作 → 受控分享记录/视图 | 只保留该回答条件、版本、出处；实时核验接收者权限，不扩为整个对话或文件/整任务分享 |

### 6.4 统一执行约束与完整链路

工具接入统一记录任务/步骤、规范化输入、输入文件/资料版本与哈希、输出/产物、来源依赖、验证状态和安全错误；具体字段不在本节另建第二套定义。身份和当前授权从服务端取得，不能接受模型给出的“已授权”。模型可组织候选公式、映射和内容，但涉及业务确认、必要输入及已有结果更新时须保留人的明确决定。

失败区分缺项待补、权限拒绝、证据不足、可恢复故障、执行结果待核对和取消；只暂停受影响项目。没有新输入、状态变化或新证据时不重复同一失败调用；提交结果不明先核对原执行，避免重复上传、修改或付费。任务有明确预算、超时、有限重试与检查点，不采用任意全局修复轮数上限，也不把单次检索或工具调用机械计为修复周期。

代表链路：

1. **资料查询**：上下文 → 目录/证据检索 → 必要原文读取 → Agent组织答案 → 主结果与证据链接。无需计算或制表时不强制调用这些工具。
2. **依据手册计算并填表**：上下文/文件检查 → 工作簿读取 → 处理范围与公式确认 → 按需检索/读取依据 → 计算准备/执行 → 修改预检及必要确认 → 实际修改 → 重算 → 成果核验/预览 → 新文件交付。缺项经原对话补充后从受影响检查点继续。
3. **多资料报告**：上下文/模板读取 → 各型号授权证据 → Agent整理对照与冲突 → 报告编制 → 核验/预览 → 可编辑成果及引用链接。

主区呈现答案、数值或文件成果、必要条件/警告和完成情况；详细证据、计算过程和修改明细通过链接查看。一次办公任务可以跨多条消息，组合多个工具；一条消息也可能只是补充或澄清。目录完整不等于实施同时完成；接下来先统一工具契约、依赖与验收矩阵，再在不改产品范围的前提下安排实现批次。实际已有能力与缺口只在 [STATUS](../planning/STATUS.md) 汇总。

### 7.1 分层与事实归属

| 层 | 保存/使用内容 | 读写和更新责任 | 生命周期及事实地位 |
| --- | --- | --- | --- |
| L1 本轮工作上下文 | 当前请求、必要且有权的条件/消息、证据、工具结果引用、缺项和可用动作 | 受控组装器经T01及工具结果构建，只取当前步骤需要的内容；模型不能把摘要写成业务事实 | 请求/步骤内派生，可释放重建；过期、失权或依赖变化即停用，不是持久事实来源 |
| L2 对话内工作条件 | 按作用域区分的已确认型号/参数/单位/范围/文件引用；推测和待确认另列 | 真实用户明确输入、更正或T17响应经服务端校验后追加修订；模型只提候选；直接浏览手册不改变条件 | 同一对话内延续，新对话不继承；作用域和来源可追溯，不改变旧任务冻结输入，也不等于企业规则批准 |
| L3 任务执行记忆 | 冻结输入/定义、工作项/步骤、计划与差异、真实确认、调用/尝试/回执、失败和检查点 | 任务/工具执行服务按真实结果与租约提交；补齐未执行项目追加resolution和execution_revision | 持久恢复依据；不能用聊天摘要、模型声称成功、旧缓存替代执行记录；未知副作用先核对 |
| L4 成果与证据历史 | 答案/计算/文件/交付的确切版本、实际输入/公式/来源及核验引用，必要证据快照 | T09/T11–T16等落实际不可变记录/产物，T16建立交付；正文不原位改写 | 保留历史与复核链，当前是否可读/可再用另行判断；永久清理遵循企业政策，不承诺永存 |

企业原件、业务适用性、内容核验、发布状态和授权仍由既有资料/权限服务维护，不是记忆自主学习的内容。L3可引用L4的不可变定义/文件/结果，同一记录不另复制；L4的原始文件仍在受控文件/资料存储，必要引文快照沿既有task_evidence保留。

### 7.2 作用域、确认与更新

1. 条件的键由conversation、scope、subject、fact_key共同确定。scope为conversation/task/work_item/file；subject来自本次已明确的设备/项目/材料绑定。同一工作项比较多型号时分别绑定subject，不能只有一个全局“当前型号”。scope更具体不代表自动覆盖：只有明确更正/覆盖关系才生效；同一变量冲突且无裁定时待确认，不能按“最近一句”猜。
2. 明示、唯一且可按字段规则校验的用户陈述可记为确认，保留原消息及实际来源片段；模型推断、指代不清、单位缺失或矛盾只能是候选。员工直接改条件或提交结构化响应是可信用户事件；模型生成的“用户已同意”不是。输入数据来自表格/资料时保留对应来源，读取成功不等于已确认业务适用。
3. 每次有效变化按expected_context_revision比较并追加新修订；原值/来源保留。撤去当前条件生成新修订的移除标记，仅影响后续使用，不假装删除旧任务/结果；不得再从旧消息/摘要自动提取该值填回当前条件，重新使用必须有新的明确输入/选择。正文永久清理是另一受控流程，不能由模型调用“忘记”绕过审计/留存。
4. 全局对话条件更正只作用后续任务。原任务尚未执行的缺项补齐按T17冻结新的执行修订；改变已用输入/公式/范围走后续任务及supersedes关系。已运行的定义、原始文件、计划hash和旧交付不被上下文新值覆盖。
5. 跨对话复用必须显式选中有权文件/成果/答案，按既有resource_refs和来源链建立新输入；只带入员工明确选中的内容，不复制旧对话全部条件。个人偏好、用户画像、自动跨对话提炼及全局默认测量值本期不做。

### 7.3 读取、组装及完成判断

读取顺序为：当前身份/用途/任务范围 → L2中匹配scope/subject的条件 → L3当前工作项与冻结执行状态 → 明确相关的L4引用 → 按当前问题检索合格资料 → 组装L1。可并行读取互不依赖的记录，但返回/外发前再核验依赖修订和当前授权。已冻结任务以其L3为执行输入，不能因T01取得较新L2就悄悄重算。

L1优先放当前问题、必要已确认条件、阻断项和最小证据；再按预算补相关消息/定义。长表格通过FileRef/RangeRef交受控工具直接读取，模型只接收必要结构/片段和实际结果，不把整本手册、全表或全部历史灌入上下文。相关消息摘要是带来源与覆盖范围的派生内容，不能取代原消息/正式证据；本期不建立另一套长期语义记忆库。

上下文缩减不得丢单位、公式定义、表头、警告、适用限制或未完成状态；预算不足则分块/增加受控读取或请求澄清，不静默截断关系。数值工具直接消费冻结计算定义，写表工具消费批准计划，不让模型按记忆重算正式数值或自行扩展写入范围。

新任务使用当前L2有效条目；历史用户陈述/已移除条件只能作为历史内容，不能冒充当前输入。已接受任务则使用其冻结FactBinding/执行修订，后续L2 head变化不使它自动改值或重算；L1有效性按实际执行范围判断，当前对话head与冻结context_revision须明确区分。

完成状态由真实步骤结果、必检及delivery决定。L2已确认、L3某次尝试成功、L4有旧文件、L1模型说完成，都不能单独把任务标为成功。重复失败指纹相同且无新输入/环境/证据时不反复调用；保留错误类别、已尝试策略、有效结果与下一行动。结果不明先reconcile，缺项等待T17，依赖变化则重新核验；开发修复周期仍按项目tasks治理，不用聊天重启清零。

### 7.4 权限和失效机制

记忆保存与当前使用资格分开。层内摘要、文件名、抽取常量和条件值同样继承来源依赖，不因“已记住”永久放行。沿用保守整任务/整成果门禁，不借记忆按段落自动脱敏、拆开授权或省略实际依赖。

| 变化 | L1 | L2 | L3 | L4及恢复方式 |
| --- | --- | --- | --- | --- |
| 用户明确改条件/取消当前条件 | 新调用重建；旧bundle不用于后续 | 追加有来源新修订，不改旧记录 | 已冻结任务不变；未执行缺项经绑定响应继续；改已执行内容建新任务 | 原成果条件/版本保持，关联新结果 |
| 多设备/项目条件冲突 | 只装当前subject必要信息，冲突可见 | 不跨subject覆盖，待明确裁定 | 仅相关项目待补，其他依赖满足项目按已有门禁执行 | 不把局部完成说成全部完成 |
| 文件hash/计划/映射变化 | 相关bundle失效 | 文件绑定值需重验，不能按相同文件名替换 | 旧预检及覆盖确认不可再用，未知写入先核对 | 旧文件/快照保留确切hash；新内容新对象 |
| 手册变superseded | 新正式查询/计算不装旧版依据 | 来源绑定条件用于新任务前重新确认适用 | 未执行的正式步骤重新过版本门禁，不自动混用新版公式 | 历史结果按既有当前权限/核验门禁可读并标历史；主动新查/新算不改旧结果 |
| 撤回、内容核验blocked或关键定位不可靠 | 不装正式依据 | 当前use_state受限/待核验，旧确认不等于仍可用 | 停止相关正式处理/提交，返回原因 | 已保存结果/原文分别沿各自既有门禁，不能从快照旁路；修复/重新核验后重查 |
| 撤权、账号停用或资料删除 | 清除相关缓存/在途上下文资格，返回前再次拒绝 | 派生值也不可读/用于新步骤；不靠隐藏引用保留摘要 | 旧租约/身份不得提交结果，允许所有者安全取消；完整任务门禁不放宽 | 阻断相关正文/预览/下载/分享，最小安全状态仍可见；重新获准后也要重验资格 |
| 浏览器登出/会话过期 | 交互bundle和页面内容失效 | 无有效交互身份不读取 | 已接受后台任务依据任务授权及当前owner/权限运行，不复用旧cookie；停用/撤权仍停止，登出不自动等于取消 | 结果仅待重新认证/鉴权后可见，不自动发给旧会话 |
| 工具/模型/索引/引擎配置变化 | bundle/cache指纹变化，按需重建 | 事实来源不自动改写 | 新执行不能重用旧环境成功回执；有证据表明旧结果错误时走核验/修正 | 旧记录保留执行版本；新预览/重算新版本，不将升级本身谎报旧结果失败 |
| 确认过期、拒绝、来源或计划hash不符 | 不装成可执行批准 | 不升级候选为确认 | 对应request/resolution不再可执行，需新计划/明确响应 | 原确认记录用于追溯，不当作永久授权 |
| 达企业留存/永久清理条件 | 移除派生缓存和可恢复正文 | 相关内容清理/墓碑化，不再进入上下文 | 先禁用读取，再清理调用/输入/计算/确认中的相关正文；按政策保留最小元数据 | 既定删除流程覆盖私有快照、派生文件/索引及恢复副本；不可变性不阻止获准清理，也不能保存副本旁路 |

权限变化不要求先等TTL到期；缓存有效期只是资源管理，不能代替读时鉴权。外部服务已接收的数据或员工已下载文件不能声称可即时追回，仍按既定外发/留存范围管理；在途调用返回后若资格变化，不进入正式结果/后续上下文。

## 8. 知识管理员治理服务与办公链路衔接

2026-11-17设计，尚未实施。完整页面和五条流程统一在[知识管理员方案](../design/知识管理员界面与对接方案.md)，HTTP及逻辑记录在[API17](../api/接口设计.md#17-知识管理员完整工作区对接设计)/[数据库17](../database/数据库设计.md#17-知识管理员维护记录与一致性设计)。本节补齐6.3的管理角色服务，不新增第21项员工工具或独立管理记忆服务。

### 8.1 责任和边界

建议资料/处理任务/员工反馈三个入口；资料为核心对象，版本下保存原件、来源、精确解析批次、核验集、实际业务确认、发布/撤回及索引就绪投影。模型可辅助定位差异，管理变更必须绑定真实认证操作、资源权限和证据；不设置通用模型HTTP写网关。

复用已有上传/文件、解析/任务、授权、索引、审计/outbox底座，补齐领域记录和页面投影，而非把所有管理动作改为办公Agent工具。相比直接扩宽T01/T17/T20，分开维护契约能保留员工对话、条件确认、反馈与专业业务判断的边界；相比新建管理平台，现有资源/任务机制更省集成成本。授权审批business_approvals不复用为手册适用确认。

外部实际确认人承担业务判断；知识管理员记录并核查依据，维护内容和发布；系统管理员按批准规则配置权限/服务，不因运维角色获取正文或代作业务决定。文件等级/类别登记不产生授权，DM不能借上传或反馈扩大自己范围；同人明确兼任允许，未规定额外双人强制审批。

### 8.2 发布和一致性

用户本轮已确认发布前完成业务依据核实、精确解析批次核验及关键专业确认，发布与索引启用仍分开；这收敛旧“发布独立于解析”的宽泛描述，已获2026-11-17用户明确确认。核验选择必须绑定run/chunk/block/内容及定位，不能按最新解析时间猜选；单文档仍只支持一个现行修订。

预检只为用户展示影响，最终锁定事务重查身份、DM、确认/核验/hold、版本和授权修订，更新现行指针与回执/outbox。KM才可启用整库索引，单份DM不能看到完整来源清单。活动索引未覆盖新现行版时明确等待，不以旧历史版顶替。撤回发布与业务停用分开；撤回不自动复活旧版，不改写旧回答。

权限撤销、核验退回、保护性暂停或版本撤回的当前门禁实时生效；outbox负责派生索引、缓存及反馈提示更新，消费延迟不能成为越权或使用失效资料的窗口。反馈回复不调用业务确认/发布接口；受理关系取当前处理范围与全部依赖权限交集，没有接收人保持安全待分派。

草稿参考与正式使用分开：2026-11-17用户确认DM可按API17.6/数据库17.6显式开放精确draft原件仅供当前有DR的员工人工参考；默认草稿仍隔离。参考状态不增加ACL，不给T04或正式T05/L1模型上下文正式资格，不替代发布/核验/索引。T03/网页原文目录只投影当前可见对象，关闭与撤权在读取时生效，不等待派生清理。

单纯配置页无法支撑撤权与恢复核对，另建管理平台又会重复状态。建议现有FastAPI集中领域命令、当前权限/用途校验和安全页面投影，后台与Worker复用同一权威记录。operations.read只读；任务控制、凭据写入、备份、恢复和审计导出需明确细分能力/平台范围，不能通过system_admin一键获得业务正文。新增权限码由受控种子/部署管理，不在网页开放任意脚本规则。

### 10.2 服务与执行一致性

服务配置按生成/向量/解析/可选重排分别版本化，连接测试、能力验证、逐服务数据准入、健康、费用独立。BGE-M3/MinerU及Pi方向沿用，具体供应商/账号/部署能力未定保持未知。秘密只以受控引用使用，Pi Runner不持密钥；主回答/摘要/压缩等均经API18当前配置/许可/预算和最终payload门禁，不增加额外外发出口。

启用/切换以精确配置、网络目的地、凭据和策略修订核验，不自动换供应商重发。向量配置变更产生兼容性检查/新索引，业务索引由KM构建启用；解析重跑新批次需重新核验，系统管理员不改业务确认或发布状态。恢复业务任务按原owner/冻结计划/预算/真实回执，不以管理员身份重做写表或代员工确认。

### 10.3 恢复与四层责任

用户2026-11-17已确认生产恢复流程：先隔离验证完整性，追平当前撤权/删除/账户停用，验证通过并由获准人员确认后才切生产。该确认只覆盖设计，不是当前执行生产恢复的批准；RPO/RTO、密钥托管、窗口和实际责任人仍待企业确定。

备份须覆盖一致数据库与引用对象，原件/解析/成果及需保留的Pi内部记录受同样数据边界；服务端加密传输，管理操作权不提供原包下载。恢复默认关闭出站/派发/分享/SDK执行，使用独立于旧快照的现行治理记录追平，治理来源不完整则保持隔离。旧会话/租约/许可/缓存epoch不能复活；旧outbox/SDK命令不直接回放。治理及审计记录跨恢复保留并合并，切换期间最新变更须重新验证，不能以数据库还原完成替代业务可用。

运维L1用OperationsMemoryView安全投影；纯后台不写员工L2；L3复用控制/测试/备份恢复的真实任务与回执；L4保存配置/审批/审计/恢复证据，备份存储不授予员工业务内容读取权。权限/服务/治理epoch变化作用于查询、计算、表格和报告链路，L1重组、来源派生L2待复核、L3执行/提交/交付重验、L4历史read/use分离；不自动覆盖旧成果或重置失败/费用预算。

20工具逐项映射见界面方案第5节：T18只共享受控运行底座，T17不代确认，T19不分享SDK/备份/日志，T20不将配置者变受理人。宿主root/数据库超级权限需企业另管，应用授权不声称消除其底层物理访问能力。当前实现和缺口只在STATUS汇总，SA-01–14及Pi/既有权限恢复验收仍待实际执行。
